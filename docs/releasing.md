# Releasing

How a release is made. A release is a `v*` tag; the tag builds the installers and makes a **draft** GitHub release. Nothing is
published until a person presses Publish.

## What is automated

Pushing a tag such as `v0.2.0` runs the `build` workflow, which:

1. checks the tag equals `v` plus the version in `app/package.json` (`app/scripts/check-versions.mjs`);
2. runs the engine tests and builds the installers on macOS (Apple silicon and Intel), Ubuntu and Windows;
3. writes a `SHA256SUMS-<system>.txt` per system and signs everything with build provenance (see [SECURITY](../SECURITY.md));
4. makes the SBOMs (CycloneDX, app and engine) and attests them;
5. the `release` job makes a **draft** release with notes generated by GitHub from the merged pull requests since the previous
   tag, and attaches the installers, the checksum files and the SBOMs. A tag with a `-` in it (`v0.2.0-beta.1`) is marked pre-release.

The tag steps only run on tags, so a pull request cannot exercise them. The version check does run on every push (it is part of
`npm run links:check`).

## What is not set up (be honest in the release notes)

- **macOS signing and notarisation: not set up.** There is no Apple Developer certificate and no secrets for one, so the app is
  unsigned and not notarised; macOS shows a warning on first open ([Troubleshooting](troubleshooting.md)). Do not write "signed" or "notarised" in notes.
- **Windows code signing: not set up.** Windows shows SmartScreen. The build provenance and SHA-256 files are the only integrity evidence.
- No installer has been smoke-tested by the workflow; step 5 below is by hand.
- `CHANGELOG.md` is not generated by any script in the repository. The draft release notes are the generated list; copy them into
  `CHANGELOG.md` by hand after publishing (one section per tag).

## One version

`app/package.json` holds the version. These must match it, and `app/scripts/check-versions.mjs` fails otherwise:
`engine/pyproject.toml`, `app/package-lock.json` (two places) and the `engine` entry in `engine/uv.lock`.

To bump to `X.Y.Z`:

```bash
cd app && npm version X.Y.Z --no-git-tag-version      # package.json and package-lock.json
# edit engine/pyproject.toml: version = "X.Y.Z"
cd ../engine && uv lock                                # updates only the engine entry in uv.lock; check the diff is one line
cd ../app && node scripts/check-versions.mjs           # must say all versions agree
```

Commit that as a pull request ("Release X.Y.Z"), merge it, then tag the merge commit.

## Checklist

1. All checks on `main` are green (three systems, engine-e2e, e2e, visual, sbom, codeql).
2. Locally: `cd engine && uv run pytest -q`; `cd app && npx tsc --noEmit && npm run i18n:check && npm run links:check && npm run build`.
3. Bump the version as above and merge it.
4. Tag the merge commit and push the tag: `git tag vX.Y.Z <commit> && git push origin vX.Y.Z`. Wait for the `build` run (the `release` job is last).
5. Smoke test the installers from the draft on each system you claim to support (macOS, Windows, Linux): install, open, transcribe
   `docs/samples/test-interview-english-two-voices.m4a`, export, quit. Use the [compatibility matrix](compatibility.md) and write down
   what you did not test.
6. Check checksums and provenance of at least one file per system ([SECURITY](../SECURITY.md)).
7. Edit the draft notes: say plainly that the builds are unsigned, add anything known to be broken, and note the systems you did not test.
8. Publish the draft (a person, in the GitHub web page or `gh release edit vX.Y.Z --draft=false`), then update `CHANGELOG.md`.

If the build fails, delete the tag (`git push origin :refs/tags/vX.Y.Z`), fix on `main`, and tag again. A tag that failed after the
draft was made needs the draft deleted first.
